# Production OTP (Fast2SMS) and Razorpay — design, setup, verification

Everything below is implemented in the repository. **Nothing has been run against the
real Fast2SMS or the client's Razorpay account** (no credentials were available when this
was written); the verification table at the end says exactly what was and was not proven.

## 1. How sign-in works now

```
app/login.tsx → supabase.auth.signInWithOtp({phone})
                    │  Supabase Auth GENERATES the 6-digit code, stores it, enforces expiry,
                    │  the resend cooldown and the per-IP / per-hour send limits
                    ▼
        Send-SMS hook  ──►  functions/send-sms-hook  (signed request, Standard Webhooks)
                               • verifies the signature (rejects anything unsigned/stale)
                               • India-only check, per-number + global send budget
                               • calls Fast2SMS (GET /dev/bulkV2, Authorization header)
                               • writes sms_delivery_log (masked number, request id)
                    ▼
        Fast2SMS ──► handset                       Fast2SMS ──► functions/fast2sms-dlr
                                                      (delivery report: accepted → delivered)
app/otp.tsx → supabase.auth.verifyOtp({phone, token})   ← the ONLY place a code is checked
                    ▼
        auth.users.phone_confirmed_at is set → trigger creates the profile (migration …15)
```

Supabase Auth stays the identity system. There is **no custom OTP table and no client-side
verification flag**: the app never sees, stores or compares a code; the hook only *delivers*
the one Auth gives it.

Replaces: there was no MSG91 integration anywhere in the code or the live Supabase config
(the live provider was `twilio` with every credential empty, so real SMS never worked).
Only the fixed-code QA numbers could sign in.

### What protects the flow

| Threat | Protection | Where |
|---|---|---|
| Guessing the code | 6-digit code, 5-minute validity, verification rate-limited per IP | Supabase Auth |
| Code reuse | Auth invalidates a code once used or superseded | Supabase Auth |
| Resend flooding | 60 s between codes per number; app timer matches (60 s) | Auth `sms_max_frequency` + `app/otp.tsx` |
| SMS pumping / wallet drain | per-number budget (5, then 1 per 10 min), global 200/hour, India-only, Auth's per-IP and per-hour limits | `_shared/smsHook.ts`, Auth config |
| Forged hook calls | HMAC-SHA256 Standard Webhooks signature, 5-minute replay window, fail-closed without a secret | `_shared/standardWebhooks.ts` |
| Limiter outage | nothing is sent (fail closed) | `_shared/smsHook.ts` |
| Provider outage / timeout | 4 s cut-off (Supabase hooks have a short time budget, about 5 s — the page I read does not state it, so 4 s is deliberately conservative); generic message; logged | `_shared/smsHook.ts` |
| Leaking the code | never logged, never stored; the request URL (which holds it) is never logged | `_shared/smsHook.ts` |
| Phone-number enumeration | Auth answers identically for known and unknown numbers; failures are generic | Auth + `services/authErrors.ts` |
| Profile for an unverified number | profile is created only when `phone_confirmed_at` is first set | migration `20260827000015` |
| Duplicate accounts | `auth.users.phone` is unique; profile insert is `on conflict do nothing` | Auth + migration |

Observed live: when the hook refuses or fails, Supabase Auth hides the hook's own status/message and
answers the client with its generic `500 unexpected_failure` ("Service currently unavailable due to hook").
`services/authErrors.ts` turns that into "We couldn't send the code right now. Please try again in a few
minutes." — so the customer never sees *why* (balance, template, rate limit), and the app cannot tell a
rate-limit refusal from an outage. The reason is in `sms_delivery_log` and the function logs.
Observed live: the fixed-code QA numbers never reach the hook (0 log rows), and a failed hook leaves no
auth user and no profile behind.

Not implemented (needs a decision and keys from you): **CAPTCHA** on the login screen
(Cloudflare Turnstile/hCaptcha) — the strongest defence against SMS pumping from many IPs.
Until then the budgets above are what limits the damage.

## 2. Environment variables (names only — never put values in git, `.env`, Expo config or chat)

All of these are **Supabase Edge Function secrets** (`supabase secrets set …` or Dashboard →
Edge Functions → Secrets). None may ever be an `EXPO_PUBLIC_` variable; the mobile app
gets only the Supabase URL and the anon key. `tests/unit/no-client-secrets.test.mjs`
enforces this.

| Name | Used by | Required | Meaning |
|---|---|---|---|
| `SEND_SMS_HOOK_SECRETS` | send-sms-hook | yes | Signing secret Supabase uses for the hook (`v1,whsec_…`). Generated by `configure-auth-sms.mjs enable`; several may be given separated by `\|` for rotation |
| `FAST2SMS_API_KEY` | send-sms-hook | yes | Fast2SMS "Dev API" authorization key |
| `FAST2SMS_ROUTE` | send-sms-hook | yes | `dlt` (production, branded) or `otp` |
| `FAST2SMS_SENDER_ID` | send-sms-hook | route=dlt | 3–6 character DLT-approved header |
| `FAST2SMS_TEMPLATE_ID` | send-sms-hook | route=dlt | The template/message id from Fast2SMS **DLT Manager** |
| `FAST2SMS_TEMPLATE_VARIABLES` | send-sms-hook | no | `\|`-separated values for the template's `{#var#}` slots; `{otp}` is replaced by the code. Default `{otp}` |
| `FAST2SMS_DLR_TOKEN` | fast2sms-dlr | for delivery receipts | Random string you generate; goes in the webhook URL |
| `SMS_PHONE_BURST`, `SMS_PHONE_REFILL_SECONDS`, `SMS_GLOBAL_PER_HOUR`, `FAST2SMS_TIMEOUT_MS` | send-sms-hook | no | Tuning (defaults 5, 600, 200, 4000) |
| `RAZORPAY_KEY_ID` | create-/verify-razorpay-… | yes | Client's Razorpay Key ID (public identifier) |
| `RAZORPAY_KEY_SECRET` | create-/verify-razorpay-… | yes | Client's Razorpay Key Secret |
| `RAZORPAY_WEBHOOK_SECRET` | razorpay-webhook | yes | The secret you type into the Razorpay webhook form (≠ the Key Secret) |
| `RAZORPAY_ACCOUNT_ID` | razorpay-webhook | recommended | Client's `acc_…` id; events from any other account are ignored |

Provided automatically by Supabase: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`.

Local tooling only (never in the app): `SUPABASE_ACCESS_TOKEN` (used by the CLI and
`supabase/scripts/configure-auth-sms.mjs`). Anything pasted into a chat must be treated as
leaked and revoked afterwards.

Generate random values with `node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"`.

## 3. Fast2SMS setup (do this before enabling the hook)

Facts below are from docs.fast2sms.com; items marked ⚠ could not be confirmed without an account.

1. **Account readiness.** State of *this* account when checked on 2026-10-27 (read-only API calls, no
   SMS sent): the API key is valid; wallet ₹50 (≈200 SMS); the `otp` route answers **996 "complete website
   verification — visit the OTP Message menu or use the DLT SMS API"**; **DLT Manager lists no sender (header)
   and no template**, so the `dlt` route (which answers 406 "Invalid Sender ID" for an unknown sender) cannot
   send either. **So no real OTP can be delivered until you complete ONE of:** (a) website verification in the
   Fast2SMS dashboard → route `otp`; or (b) DLT registration (entity, header, OTP template) added in DLT
   Manager → route `dlt`. Other refusals to expect: 999 (a first wallet recharge of at least ₹100 is required),
   416 (insufficient balance). The API key comes from Dev API.
2. **Choose the route.**
   * `dlt` — recommended. India's TRAI rules need a registered business **Entity**, an approved
     **Header (sender id)** and an approved **OTP content template** on the DLT portal of your
     operator, then added in Fast2SMS → DLT Manager, which gives a **template id**. The code only
     fills the template's `{#var#}`. Suggested template (the OTP as the only variable):
     `{#var#} is your OTP to log in to Govind Pansari. Do not share it with anyone.`
     The SMS shows your sender id and wording.
   * `otp` — works without DLT work of your own (KYC + recharge still required); Fast2SMS composes
     a generic message ("Your OTP: 123456") and accepts a numeric code only.
   The hook has **no default route**: it refuses to send until `FAST2SMS_ROUTE` is set.
3. **Set the secrets** (you type the key on your own machine — do not paste it anywhere else):
   ```powershell
   cd "F:\Govind Pansari"
   $env:SUPABASE_ACCESS_TOKEN = "<a freshly created token>"
   $s = Read-Host "Fast2SMS API key" -AsSecureString
   $k = [Runtime.InteropServices.Marshal]::PtrToStringAuto([Runtime.InteropServices.Marshal]::SecureStringToBSTR($s))
   npx supabase secrets set "FAST2SMS_API_KEY=$k" FAST2SMS_ROUTE=dlt FAST2SMS_SENDER_ID=<HEADER> FAST2SMS_TEMPLATE_ID=<ID> --project-ref swgwcsfnimodloakamtv
   Remove-Variable k, s
   ```
4. **Deploy the functions** (after the migrations in §5): see §6.
5. **Turn the hook on** (generates the hook secret, never printing it; sets OTP validity 300 s, 60 s
   between codes, 200 codes/hour):
   ```powershell
   node supabase/scripts/configure-auth-sms.mjs enable
   node supabase/scripts/configure-auth-sms.mjs status
   ```
   `disable` turns the hook off again immediately.
6. **Delivery receipts** (optional but recommended — without them you only know "accepted"):
   set `FAST2SMS_DLR_TOKEN`, deploy `fast2sms-dlr`, then in Fast2SMS → Webhooks → Create webhook:
   service SMS, "Standard Webhook", method POST, content type JSON, URL
   `https://swgwcsfnimodloakamtv.supabase.co/functions/v1/fast2sms-dlr?token=<FAST2SMS_DLR_TOKEN>`.
   ⚠ Fast2SMS documents no webhook signing, so the secret token in the URL is the only
   authentication; the endpoint can only update `sms_delivery_log`. ⚠ The docs do not state that the
   webhook's `request_id` equals the id returned by the send call; the function also matches on `udf1`
   (we pass our own row id there on the `dlt` route). Check once after the first real send:
   ```sql
   select status, route, request_id, dlr_status, created_at from sms_delivery_log order by created_at desc limit 10;
   ```
   `accepted` rows that move to `delivered` prove the correlation works.

### Provider failure behaviour

| Fast2SMS says | Logged as | Customer sees |
|---|---|---|
| 416 insufficient balance | `insufficient_balance:416` | "We couldn't send the code right now…" (you must top up — watch `sms_delivery_log`) |
| 411 / 405 invalid number | `invalid_number` | "We can't send a text message to that number." |
| 995 spam (same number repeatedly) | `rate_limited:995` | "Too many codes requested…" |
| 412/413/414/409 key or IP problems, 415 account disabled, 996/999 KYC / recharge | `auth` / `account` | generic "couldn't send" |
| template / sender (406, 424, 425, 500…) | `template` | generic |
| timeout / network / 5xx | `timeout` / `unavailable` | generic |

## 4. Razorpay: moving to the client's own account

Audit result — integration points: `create-razorpay-order` (creates the Razorpay order, returns the
public Key ID), `verify-razorpay-payment` (app callback), `razorpay-webhook` (server-to-server),
`confirm_payment()` / `confirm_payment_from_webhook()` (idempotent state changes), checkout in
`app/checkout.tsx`. The app has **no** hard-coded Key ID — it uses the one the server returns, so
moving accounts is purely a secrets change.
Refunds: **there is no refund automation** anywhere (only an `orders.refund` permission). Refunds are
done by hand in the Razorpay dashboard *of the account that took the payment*.

### Security fixes made while auditing (migrations `…13`, `…14`)

* **A customer could pay a small order and have it accepted for a large one.** The link between an
  application order and a Razorpay order (`set_payment_gateway_order`) could be called by any signed-in
  customer with an id of their choosing, and `verify-razorpay-payment` checked only the signature (which
  is valid for the small, genuinely paid Razorpay order) — never the amount. Now: the link is made only
  by the server (`bind_payment_gateway_order`, service role), the old function is revoked from clients,
  and verification additionally fetches the payment and order from Razorpay and requires payment id,
  order id, currency INR, amount = order total, a Razorpay order created *for this application order*, and
  status `captured`. (`tests/unit/razorpay.test.mjs`.)
* **Merchant tracking.** `payments.gateway_key_id` records the Key ID that created each gateway order.
  `NULL` = created before tracking = the previously configured account. An order started under another
  merchant is reported as "payment account changed" and is **not** recorded as a failed payment.

### Switching over

1. In the **client's Razorpay dashboard**: finish activation/KYC, generate **Live** API keys, and make sure
   **auto-capture** is on (the app treats only `captured` as paid; `authorized` stays pending).
2. Before switching, confirm nothing is mid-payment:
   ```sql
   select count(*) from payments p join orders o on o.id = p.order_id
   where p.method <> 'cod' and p.status = 'pending' and o.status not in ('cancelled','delivered');
   ```
   (It was 0, and no prepaid payment had ever been completed, when this was written.)
3. Set the secrets (same secure pattern as §3):
   `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`, `RAZORPAY_ACCOUNT_ID`.
4. Create the webhook in the client's dashboard: URL
   `https://swgwcsfnimodloakamtv.supabase.co/functions/v1/razorpay-webhook`, active events
   `payment.captured` and `order.paid`, secret = `RAZORPAY_WEBHOOK_SECRET`.
5. Do a **Test-mode run first** (test keys + test cards/UPI from Razorpay's docs) before the live keys.
6. Old merchant data: payment ids, orders and refunds made under the previous account **cannot be moved or
   verified with the new keys**. They stay reconcilable (`gateway_order_id`, `payment_reference`,
   `gateway_key_id is null`) in the old account's dashboard.

## 7. Testing it end to end

**Sign-up / OTP / profile (real phone, after §3):**
1. Use a number that is *not* in the QA list. Request a code → SMS arrives within ~10–30 s.
2. In SQL: `select status, route, request_id from sms_delivery_log order by created_at desc limit 1;`
   → `accepted`, later `delivered`.
3. `select count(*) from profiles where phone = '91XXXXXXXXXX';` → **0** before you enter the code, **1** after.
4. Enter a wrong code → "incorrect or has expired"; the right code → signed in; request again and sign in
   again → still exactly one profile and the same user id.
5. Press Resend before 60 s → button inactive; force it via the API → rate-limit message.

**Payment (Razorpay Test mode first):**
1. Place a UPI/card order. The order must NOT appear in the store's New queue or the admin Active list while
   unpaid.
2. Pay with a Razorpay test method → order becomes paid and appears for acceptance.
3. Fail a payment (test failure number) → order is not marked paid; retry works.
4. Kill the app right after paying → the webhook marks it paid within seconds
   (`payments.provider_response->>'source' = 'webhook'`).
5. `select order_id, status, gateway_order_id, gateway_key_id from payments order by created_at desc limit 5;`
   → `gateway_key_id` is your Key ID.

## 8. Go-live blockers and remaining requirements

* **QA sign-in numbers.** The live project has 39 phone numbers with a fixed OTP, including the
  super-admin QA number. Anyone who knows the code can sign in as them. Remove them before launch:
  `node supabase/scripts/configure-auth-sms.mjs status` shows the count; clear the list in Dashboard →
  Authentication → Providers → Phone → test numbers (or PATCH `sms_test_otp` to an empty string).
  Your QA suites need them, so keep them until the real-SMS test above has passed.
* DLT: entity registration, header (sender id) approval and OTP template approval take operator time
  (often days) — start now. Until approved use route `otp`.
* Fast2SMS account: KYC, ₹100 first recharge, enough balance (watch `sms_delivery_log` for `insufficient_balance`).
* Razorpay: client's account activation/KYC, live keys, auto-capture, webhook.
* CAPTCHA on the login screen (recommended, not built).
* The app is on Play internal testing: users on an old build keep working (the app code is unchanged
  apart from error wording and a 60 s resend timer); rebuild the AAB to ship those two small changes.

## 9. Rollback

* SMS: `node supabase/scripts/configure-auth-sms.mjs disable` (hook off immediately).
* Profiles: `drop trigger on_auth_user_phone_confirmed on auth.users;` and re-apply the previous
  `handle_new_auth_user()` (kept in migration `…15`'s header notes).
* Payments: redeploy the previous functions from git; `grant execute on function
  set_payment_gateway_order(uuid,text) to authenticated;` only if the old `create-razorpay-order` is redeployed.

## 10. What was verified, and what was not

Automated suites: `npm run test:unit` (pure logic, the whole hook flow with a faked provider, signatures,
the no-secrets scan) and the live checks in `supabase/tests/` — `otp-auth.test.mjs`,
`profile-after-verification.test.mjs`, `payment-binding.test.mjs`.

| Area | Evidence | Status |
|---|---|---|
| Hook signature scheme | my verifier vs the official `standardwebhooks` library, both directions; and real Supabase Auth's signed call was accepted by the deployed function | **verified** |
| Hook decision flow (limits, errors, timeout, no leaks) | `tests/unit/sms-hook.test.mjs` with a faked provider; mutation-tested (breaking the limiter / replay window / error mapping makes tests fail) | **verified (faked provider)** |
| Fast2SMS request format | built from docs.fast2sms.com; key validity and the error shapes for `otp` (996) and `dlt` (406) confirmed with real calls that cannot send | **partly verified** |
| A real SMS reaching a phone | needs website verification or DLT registration on the account, then a test from a non-QA number | **NOT verified** |
| Delivery receipts (`fast2sms-dlr`) | endpoint auth and update logic tested; Fast2SMS's real payload / request-id correlation untested | **NOT verified live** |
| Profile only after verification, no duplicates | rolled-back SQL probe on the live DB (11 checks) + negative control showing the old code created a profile at request time | **verified** |
| QA numbers unaffected, one profile per user, resend cooldown, wrong code rejected | `otp-auth.test.mjs` against live Auth | **verified** |
| Brute-force / per-IP limits, code expiry, code reuse | Supabase Auth's own mechanisms; settings read back and asserted, but not exercised with a real code | **configured, not exercised** |
| Razorpay: customer can't choose the gateway binding; forged signature refused; other-merchant order handled | `payment-binding.test.mjs` live (an unpaid order created on the configured Razorpay account, then cancelled) | **verified** |
| Razorpay amount / currency / order-binding / captured checks | `tests/unit/razorpay.test.mjs` (pure rules); the deployed function applies them, but no real Razorpay payment was made | **verified (rules), not with a real payment** |
| Razorpay webhook | refuses everything until `RAZORPAY_WEBHOOK_SECRET` is set (confirmed live); a real event untested | **NOT verified with a real event** |
| Switching to the client's account | secrets only; the keys currently configured are LIVE keys of an account that may not be the client's | **needs the client's keys** |
